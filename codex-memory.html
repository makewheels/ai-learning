两层记忆:一张规则卡 + 一个整理阿姨

AGENTS.md = 你手写贴墙上的过塑规则卡(agent 无权改);Memories = 夜里的整理阿姨(你走后把散落便签合并成一份摘要)。

生成 + 更新:延迟、后台、两个模型

实例 1 · 一次会话,Phase 1 抽出什么
会话里发生的(节选)
  user:  staging 的 deploy 脚本会静默吞错误,排查时用 prod 那种带输出的跑法
  user:  这仓库测试用 make test,别直接 pytest
  agent: …改代码 / 跑测试 / 部署…
模型 A 抽出的候选
  · staging deploy 脚本静默吞错误;诊断改用 production 风格输出
  · 本仓库测试入口是 make test(不要直接 pytest)
落盘前  扫密钥 → 无 → 写入 raw_memories.md,等 Phase 2 合并
实例 2 · 下次会话「整读」的那份 memory_summary.md
# 项目 myapi · Rust + Axum + SQLx
- 测试入口 make test,不要直接 pytest
- staging(10.0.1.50)deploy 脚本吞错误;诊断用 prod 输出风格
- 部署 make ship-prod(make ship 已废弃)
- 用户偏好简洁回答
→ 整份塞进上下文(超预算就截断);要更细才去 grep MEMORY.md
开关
默认关:[features] memories = true 开启;use_memories(读)/ generate_memories(写)可独立开关;会话内 /memories 临时控制。

文件长什么样:目录 + 分点,没有数据库

~/.codex/memories/
├── memory_summary.md      # 下次会话最先「整读」的整合视图(实例 2 就是它)
├── MEMORY.md              # 合并后的记忆正文;需要细节时 grep 它
├── raw_memories.md       # 整合前的原始抽取输出(实例 1 的候选)
├── skills/
│   └── <name>/SKILL.md   # 与某个技能相关的记忆
└── rollout_summaries/
    └── <slug>.md         # 每个会话的摘要,喂给整合流程

官方定位是「生成态」:能看,但不建议手改;要改稳定规则去改 AGENTS.md。Hermes 恰恰相反,鼓励 agent 主动编辑。

冲突怎么解:模型裁决 + 时间淡出(偏「软」)

实例 3 · 一条冲突被「合并」消化(模型 B,不是字符串去重)
旧记忆    部署用 make ship
新候选    部署改用 make ship-prod(make ship 已废弃)
合并结果  部署用 make ship-prod(make ship 已废弃,2026-09 起)
同时      合并前获取全局锁,防止两个后台整合互相覆盖
  • 合并即调和:模型 B 读新候选 + 整份旧库,裁决谁覆盖谁、哪些并成一条(见实例 3)。
  • 全局锁:同一时刻只有一个整合在写,防并发覆盖(写冲突)。
  • 30 天衰减:没被召回的记忆 / 没用的 rollout 自动剪除,过时内容靠「淡出」清理。
  • AGENTS.md 就近覆盖:越深越具体优先,AGENTS.override.md 压过同级 AGENTS.md。
代价
软裁决 = 滞后 + 不可精修。要确定性/跨机器/跨工具,得上 Mem0 / MemoryRouter / Cognee 外挂层(见 资源链接)。
